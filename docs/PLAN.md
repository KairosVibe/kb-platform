> R3 定位与交付：通用知识管理与 AI 问答平台，用于真实工程落地及简历展示；不转为电商/售后专用产品。继承 R2 功能编号和安全契约。当前只修订文档，尚未确认进入开发。详见 [交付、评测与文档确认](DELIVERY-EVALUATION.md)。

版本：2026-09-16 R3；当前规划，不是完成记录。

## 1. 文档职责

- 用户原始需求为范围依据；[DESIGN_REVISION](DESIGN_REVISION.md)记录已确认修订；[PRD](PRD.md)定义60个功能点验收；[FUNCTION-MAP](FUNCTION-MAP.md)定义函数与数据契约。
- [ARCHITECTURE](ARCHITECTURE.md)解释当前依赖与状态；[DEPLOYMENT](DEPLOYMENT.md)定义发布恢复边界。两份不另立相反规则。

## 3. 阶段与出口

1. D0 文档确认：当前阶段。先收敛范围、图文、状态、接口和评测口径，用户确认前不开发。
2. D1 最小贯通：权限对齐、最小身份组织、文档解析索引、非流式授权问答与引用。权限对齐的差异清单与门禁见 [权限契约审计](PERMISSION-CONTRACT-AUDIT.md)。
3. D2 工程完整性：组织管理界面、批量导入、切片、版本删除、流式恢复、审计。
4. D3 知识运营：FAQ 审核缓存、自动挖掘、缺口闭环和看板。
5. D4 可复现交付：干净部署、评测、故障恢复、演示与简历证据。

各阶段出口以 [交付评测规范](DELIVERY-EVALUATION.md) 第 3 节为准。原 60 功能点全部保留，种子数据不替代最终管理界面，接口和数据库契约在对应模块开发前完成。

## 4. 交付与兼容性

- 当前不修改原项目快照。允许评估沿原工程隔离改造或新骨架迁入，先按REUSE-MATRIX完成基线验证；保留来源并核对依赖。
- 修改已有授权时更新对应正反例，不删除失败测试来伪装通过；旧例外测试应变为明确拒绝预期。
- 文档一致不代表代码实现；每条完成声明附运行版本、命令/操作、预期与实际结果。
- 原31–40人日是修正算术后的历史估算，不是R2承诺；新增持久任务、事件及安全闭环后应按实现拆分重估，不继续引用30–39或35–47作为精确工期。

## 5. 不能擅自裁剪的要求

登录与后端授权、四维OR、批量导入、知识生命周期、受限提示与引用、FAQ审核缓存、缺口识别、运营指标、至少一条完整问答沉淀演示。

部署规模可以按实际环境安排，但不以取消安全检查、恢复验证或把未知用量当零来降低难度。

## 9. 文档-代码同步规则

**编码前必须先更新 [FUNCTION-MAP](FUNCTION-MAP.md)，再进行实现**；确实来不及更新时，必须严格参照现有 FUNCTION-MAP 编写代码，保证代码与文档一致。每次动手前须明确检查 FUNCTION-MAP 的当前状态（§1 公共类型与字段名、§4 函数签名、其中的"实现状态"标注）。

- 新增或改名公共函数、DTO 字段、枚举成员：先改 FUNCTION-MAP，再改代码。
- 函数编号 `H01`… 为稳定编号；新增函数**追加新编号**，不重排、不复用。新增编号后同步 README 的基础函数计数。
- 逻辑字段名与 Python 属性名不一致时（如 `global` 是关键字 → `is_global`），必须在 §1 映射表登记，不允许只在代码里默默改名。
- 门禁 `backend/scripts/check_doc_code_sync.py` 的第 8 项检查是本规则的机械拦截（契约层公开符号未登记即失败），但它不能替代"先改文档"这一步。
