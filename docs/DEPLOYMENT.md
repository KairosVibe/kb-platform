# 部署、发布与恢复契约

> R3 定位与交付：通用知识管理与 AI 问答平台，用于真实工程落地及简历展示；不转为电商/售后专用产品。继承 R2 功能编号和安全契约。当前只修订文档，尚未确认进入开发。详见 [交付、评测与文档确认](DELIVERY-EVALUATION.md)。

版本：2026-09-16 R3。首版设计：单实例受控维护窗口。下列均需实现并实测，不以勾选标记表示已完成。

## 1. 拓扑与持久状态

- kb-web：前端静态文件、TLS和反向代理；对外80/443。
- kb-api：一个实例、workers=1；含服务编排与持久任务执行器。MySQL、API只在内部网络访问。
- MySQL：业务、授权、持久会话、任务、消息事件、审计；持久卷。
- 文件存储：原始文档和版本文件持久卷；UUID路径，非root进程需明确所有权。
- Milvus Lite：单实例持久文件或服务实际支持的文件方式；不允许未验证的多进程共享写入。standalone为另一个部署配置，必须独立验证。
- 进程内倒排/FAQ可从持久事实重建；重启不丢失授权撤销、任务和审计。

## 2. 打包要求

1. API/Web多阶段镜像；基础镜像和构建工具固定版本或digest。不得用uv:latest生成声称可复现的生产镜像。
2. API镜像包含应用、依赖、Alembic配置及迁移目录，非root用户仅对持久数据目录可写；迁移工具缺失时构建门禁失败。
3. 显式注入版本ARG并写OCI label；/health的git revision与镜像一致。
4. secret运行时注入，不进镜像/git/日志；配置界面只显示已配置。更换secret按部署流程生效。
5. 离线包若交付，包含所有实际用到镜像、校验和、配置示例、迁移和恢复说明；不声称离线环境无需外部模型访问，须明确模型网络依赖。

## 3. 反向代理与健康

- /api/全部业务路径代理到API，不能只配置/api/chat而遗漏登录/知识/FAQ。
- 事件路径关闭响应缓冲和缓存，超时与心跳协调；X-Accel-Buffering为响应头，不把发给上游的请求头当作缓冲控制保证。
- /health仅存活与版本；/ready验证DB、索引和执行器就绪，不泄露secret。
- Docker unhealthy标记不自动等于容器重启；restart策略只处理退出等条件。要自动恢复需明确健康监督机制，防止数据库短暂故障触发循环重启。

## 4. 单实例发布顺序

1. 获取发布互斥锁，验证目标镜像及配置；记录当前镜像和DB revision。
2. 进入维护模式，拒绝新写和新问答；活动流限时排空，超时显式取消并终态落库；暂停任务领取，确保没有活跃索引写入。
3. 完成一致性备份：DB、原始版本文件、向量快照或明确的可重建数据清单，记录共同检查点。
4. 拉取并确认新镜像；以新镜像运行一次迁移job；失败停在维护模式，不跳过迁移继续切换。
5. 停旧实例、启动新实例；恢复过期租约并重建内存结构；/ready通过。
6. 执行登录、授权拒绝、有效问答、FAQ撤权等冒烟；通过后解除维护；记录停机时间和结果。

本流程不承诺零停机。蓝绿扩展需要先解决缓存失效跨实例传播、调度领导权、持久文件/向量切换、长连接排空和回滚兼容，不可用两个workers=1代替该设计。

## 5. 回滚与迁移

- expand-contract逐步实施：增加兼容字段→回填→验证新旧读写→后续版本删除旧字段。
- 回滚旧镜像前检查其是否兼容当前DB和事件/索引版本。兼容才回旧版本；不兼容走前向修复或维护窗口整体恢复。
- 不可逆迁移并不自动保证旧代码可用；禁止无证据承诺秒级回滚。
- 恢复备份会影响检查点之后数据，必须按确认的恢复目标执行；不自动用旧备份覆盖新业务数据。

## 6. 验证与运行环境

- 单元测试允许stub；MySQL事务、唯一约束、锁、迁移及Milvus行为必须真实后端集成测试，SQLite/内存不能替代。
- CI依次类型/静态检查、单元、真实后端集成、构建、扫描、发布候选、部署冒烟；未实现CI前不宣称流水线通过。
- CPU/内存/磁盘上限由压测确定。2C4G和镜像大小均不得标为实测结果，除非附版本、数据量、并发和测量证据。
- 队列有界、任务限流、日志轮转、磁盘告警；模型失败区别生成/embedding/rerank，不把本地embedding当生成模型降级。

## 7. 备份与恢复验收

1. 备份对象至少包括DB、原始文档/版本映射、模型与切片配置版本；向量若不备份，明确重建时间和成本。
2. secret独立受控恢复，不能打包明文给所有离线包读者。
3. 干净环境恢复后核验：账号撤销、四维ACL、FAQ来源权限、文档版本与引用、任务状态、审计计数。
4. 记录恢复耗时、数据检查点及实际丢失窗口；保留期和RPO/RTO由业务运维确认，不能默认7天备份已满足企业要求。

## 8. Runbook要点

- 新发布5xx：保留证据、进入维护、检查ready与迁移兼容，再选择回滚或修复。
- 缓存不一致：读侧以DB拒绝为准，安全清缓存重建，不能暂时关闭鉴权。
- 索引失败：检查任务版本/租约/错误，重试当前版本；禁止盲删全部向量。
- 模型限流：有界排队、限流和安全错误；不透明重试已输出的生成请求。
- 磁盘不足：按保留策略清理可再生/到期数据；不要删除仍被引用原文或恢复所需版本。

## 9. 已确认的演示约束（2026-09-16）

用户确认演示采用云端模型API和模拟资料，首轮格式为DOCX、文本PDF、Markdown、TXT，旧DOC和OCR后续扩展。部署说明必须列明云API网络依赖与密钥注入，不声称完全离线。

机器配置、保留期与容量已于2026-09-16确认（命令实测）：Windows 11 Home China 10.0.26200、i7-12650H（10核/16线程）、内存31.8GB、MySQL 8.0.26（服务MySQL80，集成验证前须启动）；会话消息90天、审计180天、事件7天可配置；容量初值单实例1万文档/10万切片；RPO<=24h、RTO<=4h。embedding维度冻结为1024，供应商与模型ID待选定。**本机为基础开发与演示环境，不作为生产规格**；云API密钥注入与轮换按第2节要求执行。详见 [格式与验收](FORMAT-ACCEPTANCE.md)。

### 9.1 开发/演示拓扑（D-08 / D-09 已确认）

| 组件 | 位置 | 说明 |
|---|---|---|
| 前端静态文件 | 暂未部署 | D1 起为本地 dev server；对外由反向代理承担（见第3节） |
| kb-api（FastAPI） | **Windows 宿主机** | 单实例 `workers=1`（本文件开头已定） |
| MySQL 8.0.26 | **本地 VMware 虚拟机** `192.168.62.128`（`mysql:8.0.26` 容器，**D-09 变更**） | 业务、授权、持久会话、任务、事件、审计。**2026-09-17 起不再使用宿主 `MySQL80` 服务** |
| Milvus standalone / Neo4j | **本地 VMware 虚拟机** `192.168.62.128`（CentOS 7，Docker 26.1.4） | 向量召回与图召回；容器按内核限内存。实际版本 **Milvus v2.5.5 + Neo4j 5.21.0**（另有 etcd v3.5.18 / MinIO RELEASE.2024-12-18 / Attu v2.5.10）；承载于既有 compose 项目 `rag`（`/root/rag/docker-compose.yml`） |

**为什么组件不放宿主机**：Milvus 官方不支持 Windows 原生运行（`milvus-lite` 仅 Linux/macOS），而本机无 Docker。VM 已有 Docker，因此把"必须跑在 Linux 上的组件"整体移入 VM。

**D-09（2026-09-17，用户决定）把 MySQL 也移入 VM**，宿主机只保留 kb-api 与前端 dev server。理由与代价：

- **理由**：① 数据与中间件集中在一台 Linux 机器，宿主不再承担状态；② 宿主不再需要**管理员权限**才能启动数据库服务（本机 `MySQL80` 是 `Manual` 启动，每次重启后都要人工提权启动，已验证会直接导致集成测试整体跳过）；③ 版本固定为镜像 tag，可随 compose 一起重建。
- **代价**：① 所有 DB 读写改为跨局域网（宿主 → VM 3306），延迟从"本机回环"变为"局域网"；② 宿主可用性不再是唯一依赖，**VM 未开机则后端与集成测试均不可用**；③ VM 内存仅 3.7GB，容器需显式限内存。
- **不采用的替代**：把宿主 `MySQL80` 设为 `Automatic` 启动。那样仍需管理员首次配置，且数据与中间件仍分散在两台机器上。

这与"首版单实例"不冲突：逻辑上仍是一套单实例部署，只是宿主机与状态组件分居两台机器。

**两条网络约束（部署时必须满足）**：
1. **后端 → 中间件**：`MILVUS_URI=http://192.168.62.128:19530`、`NEO4J_URI=bolt://192.168.62.128:7687`。VM 的 `firewalld` 实测为 inactive，端口无需额外放行；但这意味着**中间件对本网段可见**，仅限实验环境接受。
2. **VM → 外网（仅 `docker pull` 需要）**：VM 内 Docker 出口经 `/etc/systemd/system/docker.service.d/http-proxy.conf`。**2026-09-16 更正**：原值 `127.0.0.1:7897` 在 VM 内**并无监听**（既非本地代理，也从未有隧道接上），实测不可用；已改为宿主机在 VMnet8 上的地址 `http://192.168.62.1:7890`（宿主机 FlClash 监听 `0.0.0.0:7890`，实测经它访问 `registry-1.docker.io` 返回 401、`auth.docker.io` 返回 200）。**不需要反向隧道**——VM 可直连宿主机该端口，且不依赖 SSH 会话存活。`NO_PROXY` 已含镜像源与 `192.168.62.0/24`。
   **注意适用范围**：本项只影响后续拉取新镜像。本环境的中间件镜像**早已离线导入**（`/opt/software/*.tar`），VM 上也已有既有 compose 项目 `rag` 在运行，因此**出网不是本项目部署的前置条件**；隧道/代理断开不会影响现有容器。

**已验证（2026-09-16，命令证据）**：中间件实际启动并 healthy（etcd/MinIO/Milvus）；宿主机→VM 端口 19530/7474/7687/18080 可连；**端到端读写往返通过**（Milvus 1024 维建表→insert→search 命中自身；Neo4j Cypher 写读一致，Kernel 5.21.0）。**尚未验证**：内存压力下的长时间稳定性、本项目业务链路对中间件的实际使用，故仍不得据此声称"平台可运行"。

### 9.2 后端环境变量与向量库形态（2026-09-16，D-09 更新于 2026-09-17）

本节是后端**部署期配置**的唯一声明处；`backend/app/core/config.py` 是它的实现，两者必须一致——改默认值前先改本节。可热改业务参数不在此列（走 `config_revision` 表，见 §1）。

| 变量 | 开发/演示值 | 说明 |
|---|---|---|
| `APP_ENV` | `dev` | `dev`/`prod`。prod 下内存态刷新存储**直接失败**而非静默降级 |
| `DATABASE_URL` | `mysql+aiomysql://kb:kb_pass@192.168.62.128:3306/kb_platform?charset=utf8mb4`（**D-09：指向 VM 容器**） | ★ 集成测试库由它**派生**（库名追加 `_it`），改动它会同时移动测试目标库 |
| `JWT_SECRET` | 本机自备（≥32 字符） | 长度不足启动即失败；开发默认值例外 |
| `VECTOR_BACKEND` | `milvus_standalone` | `milvus_standalone` / `milvus_lite` 二选一 |
| `MILVUS_URI` | `http://192.168.62.128:19530` | ★ **必须与 `VECTOR_BACKEND` 形态一致**（见下） |
| `MILVUS_COLLECTION` / `FAQ_COLLECTION` | `kb_chunks` / `faq_q` | |
| `NEO4J_URI` | `bolt://192.168.62.128:7687` | 必须以 `bolt://` 或 `neo4j://` 开头（启动期校验） |
| `NEO4J_USER` | `neo4j` | |
| `NEO4J_PASSWORD` | 与 VM `/root/rag/.env` 一致 | **不进版本库**（§2 第 4 条） |
| `EMBED_PROVIDER` / `EMBED_MODEL` / `EMBED_DIM` | `qwen` / `text-embedding-v3` / `1024` | 三维度共同构成向量空间标识；D-03 已冻结 1024 |
| `DASHSCOPE_API_KEY` | 本机自备 | 云模型凭据 |
| `UPLOAD_MAX_MB` / `UPLOAD_DIR` | `20` / `./data/uploads` | 单文件上限为首版设计初值，非实测上限 |

**向量库双形态约束（已固化为启动期校验）**：

- `VECTOR_BACKEND=milvus_standalone` → `MILVUS_URI` 必须是 `http://` 或 `https://` 地址；
- `VECTOR_BACKEND=milvus_lite` → `MILVUS_URI` 必须是文件路径，**不得是 URL**；
- 只改其中一个（例如切了形态却留着旧地址）不会自然报错，而是一直连到错误形态、直到第一次检索才以"连不上/空结果"暴露，归因困难。此前这只能靠人记住 `deploy/vm/README.md` 里的提醒，**现改为启动即失败**。

**为什么默认形态是 `milvus_standalone`**：`milvus_lite` 仅支持 Linux/macOS，而本机开发平台是 Windows——lite 在本机**不可能工作**；D-08 也已确定中间件由 VM 承载。故默认值取"在本机可用"的形态。`milvus_lite` 保留为 Linux / 云端部署选项，切换时 `VECTOR_BACKEND` 与 `MILVUS_URI` **必须同时改**。

**`.env` 纪律**：实际值写 `backend/.env`（**不进版本库**）；版本库内的声明是 `backend/.env.example`。仓库此前**没有任何 `.gitignore`**，"凭据不进版本库"这条要求没有机制保障，故一并补上 `backend/.gitignore` 忽略 `.env`。

**边界**：以上都是"配置能否正确加载"的校验，**不是**"已连通中间件"的证明。连通性证据在 §9.1 的端到端往返；业务链路对中间件的实际使用仍属未验证。
